# 04 — Agent Work Order (Future Execution Contract)

**Execution status:** Prepared instructions; **do not treat this document's existence as authorization** to mutate engine code, perform external effects, trigger cloud workflows or publish a release. The user separately controls start, scope and irreversible operations.

## Roles and authority

| Actor | Subject | Authorized responsibility |
|---|---|---|
| **Owner/instructor** | Purpose, target, scope, constraints, risk acceptance and completion | Sets or changes objectives and acceptance population; approves material scope or semantic changes |
| **Architect/supervisor** | One coherent target design and evidence-based judgment | Audits current system, assigns authority and change responsibility, resolves contradiction; cannot substitute taste for objective |
| **Implementation agent** | Approved repository and implementation unit | Reads actual baseline, constructs and tests target; may not alter task purpose, control ownership, release threshold or public-private boundary |
| **Independent checker** | Exact source/version, real test inputs, results and traces | Reports observed acceptance and regression; does not change the definition of passing |
| **End user/consumer** | External interface and authorized effects | Supplies actual requests and permissions; no implicit consent to transmission inferred from generated text |

The same AI may perform multiple roles mechanically, but every report must retain distinct **instruction, implementation, observation and acceptance** records. A result generated by the implementation agent is not automatically independently verified.

## Orders

`ORDER-00`: Inspect and populate the full source/test/capability census. Record concrete source presence and reachable public routes separately. Reject anonymous `implemented` labels.

`ORDER-01`: Produce the whole-system dependency/authority diagram and compatibility contract. Preserve subject, purpose, goal and evidence identity across every interface. If a legacy abstraction prevents meeting the target, demonstrate its defect and revise upstream design.

`ORDER-02`: Assign **one accountable owner** to every state mutation, learning adoption, operation, side effect, final judgment and delivery. De-duplicate hidden judges and return paths; keep display behavior separate from action authority.

`ORDER-03`: Complete **all mandatory normal routes** in one vertical integration pass: natural text, context, relations, evidence, reasoning, calculation, writing, code, specialized modules, learning, memory, failure, output, trace and effects. Include typed adapter interfaces for all identified emerging consumers.

`ORDER-04`: Repair source and evidence integrity. Retrieval list and document body have distinct packet identities; keep time, provider, retry, failure and exact content fingerprints. Diagnostic fixed replay must not enter official LIVE scoring.

`ORDER-05`: Close learning as **memory → inference → adaptation** inside the core through both everyday and specialist entrances. Measure actual reuse and generalization on independent inputs; retain reversible evidence and invalidation.

`ORDER-06`: Close meaningful progress and failure semantics: only user-goal delta justifies adoption and approved continuation; protect original purpose and resource budget from self-referential progress. Retain actual prior outputs for follow-ups and corrections.

`ORDER-07`: Run the complete user-facing E2E acceptance matrix before judging local feature success. Diagnose failures from evidence; fix the responsible level; rerun affected tests and full regression as required. Do not build new modules when the issue is routing or state ownership.

`ORDER-08`: Reconcile version, performance, provenance and publication. Do not report new GPQA, English-input quality, general-intelligence quality, multi-OS or deployment success without current direct observations.

`ORDER-09`: Only under subsequent release authorization, cut a separately identified source/packaged version with new hashes, test and compatibility record. Preserve the beta1 source lock and all original release evidence.

## Required machine-readable progress record

For each finite work unit, report at least:

```text
unit_id
target_repo, base_commit, target_version
user_instruction_id, purpose, original_constraints
capability_ids, owned_interfaces, dependent_consumers
baseline_fact_refs, observations, unresolved_evidence
change_class, paths_changed, change_rationale
actual_test_command, environment, dataset_or_inputs, stdout_artifact
expected_vs_observed, regression_items, failure_signature
resource_and_effect_accounting, next_status
```

Use `FACT / OBSERVED / INFERRED / ASSUMED / UNKNOWN` classifications. A missing result is `UNKNOWN`, not `PASS`, and a failed command cannot be summarized as a completed task.

## Forbidden shortcuts

- Rewriting requirements to match the code that is easiest to implement.
- Replacing the full input→answer system with isolated demonstration actions or synthetic outputs.
- Copying benchmark answers, evaluation gold or future information into rule generation or prompts.
- Treating an existing `import` or 313 selected tests as proof of full product functionality.
- Re-fetching changing LIVE material and attributing resulting score differences solely to algorithm changes.
- Duplicating accepted internal functions instead of investigating the actual disconnected return path.
- Silent goal reformulation, loss of source context, deletion of evidence, hidden data release or unsanctioned cloud permissions.
- Revealing unpublished HDS theory, reconstruction crosswalks or large derived semantic artifacts.
- Mutating original `0.6.0b1` engine identity, old wheel/ZIP hashes, baseline test records, or original upstream `main`.

## Stop and escalation

Stop the affected operation when:

- A required external permission, credential, deployment or publication decision is missing.
- Existing/user instructions conflict materially or a proposed migration changes public semantics/guarantee.
- The actual source/evaluation population is unavailable and that absence would change the decision.
- A destructive or irrecoverable modification exceeds the user's authorization.
- A safety or private-theory disclosure boundary would be crossed.

Report the **exact blocked action, subject, cause, evidence and least-expansive decision needed**. Ordinary incomplete code or failing tests are engineering work to diagnose, not permission to weaken the original task.

## Completion

An implementation agent may report `COMPLETE` only when the actual user request and entire accepted register population are fulfilled, relevant independent tests passed, prior verified behavior has not regressed without a recorded authorized change, performance/portability claims are backed by measured conditions, and all source/evidence/publication boundaries are satisfied. Otherwise, report precise remaining rows and blockers; never replace completion with a progress percentage based on file count.
