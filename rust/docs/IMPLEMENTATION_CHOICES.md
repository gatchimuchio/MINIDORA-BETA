# Implementation choices and alternatives

These are concrete choices for the Rust development alpha. They implement bounded public operations under the normative [R2 architecture](../../docs/redesign/01_SYSTEM_SPECIFICATION.md); they do not redefine the engine's logical meaning or certify the full successor. Every choice remains subject to observed compatibility, resource and acceptance evidence.

## Exact numbers instead of binary floating point

`num-bigint` and `num-rational` provide arbitrary-precision integers and normalized exact fractions. They support reproducible decimal parsing, polynomial coefficients, linear transformations, rational probabilities and descriptive statistics without converting a supplied decimal through binary `f64`.

Alternatives include fixed-width integers, fixed-point decimals and floating point. Fixed-width arithmetic has useful speed/space bounds but requires explicit overflow handling; a single fixed scale does not represent every fraction; floating point requires target-specific rounding/error semantics and would not preserve the inherited exact-rational contracts. Arbitrary precision also has costs: expression/bit/term/depth/operation limits are explicit admission guards, not a claim of unlimited resources. Unsupported sizes stop rather than silently round or trim. Each operation's mathematical domain and numeral syntax are recorded separately.

Complete unitless numeric tokens take precedence over inferred unit suffixes. A shared lexical classifier and maximal numeric-prefix check prevent scientific exponents or expression fragments from becoming unit labels in scalar, CSV and grouped-table statistics or unit addition. They do not evaluate or certify expressions; the existing exact parser retains syntax, exponent, depth, operation and bit limits. Explicit units such as `eV`, `1 e3`, decimal quantities and supported rational quantities remain distinct. The ordinary-route evidence and retained pre-correction results are recorded in [the basic extraction/statistics follow-up](../audit/b04-basic-extraction-statistics-route-validation.json).

## Explicit algorithm IR to Python source

`code_generation.rs` implements the inspected `コード生成.py::関数を生成` forms as a pure source generator. The input machine seals the complete original document; Core invokes the generator, owns its report and adopts the exact source through the existing render/file receipt path. Fixed operator/call mappings and parenthesized expressions preserve the explicit algorithm. Constants remain a separate raw JSON dictionary; generated source references its keys. Input/output examples and expected values do not select the algorithm.

The shared strict JSON tree rejects duplicate keys and preserves number lexemes before constant validation, including 256-bit integers without `f64`. Identifier validation uses the locked regex XID properties intersected with Age <=15.0, excludes U+200C/U+200D/U+30FB/U+FF65, and requires NFKC stability. A local comparison of all 1,114,112 codepoint positions against CPython 3.12.14 / Unicode 15.0.0 found exactly those four extra continuation characters and no missing start/continuation characters before the exclusions. The locked regex tables are Unicode 16.0 and normalization tables Unicode 18.0; this versioned observation is not an all-string or all-runtime conformance claim.

IR nodes, expression/block depth, constructed AST size/depth, constants and source bytes have finite bounds. Source formatting differs from Python `ast.unparse`; selected independent Python AST and finite-output observations are in [the B07 audit](../audit/b07-code-generation-route-validation.json). This Rust path introduces no runtime interpreter/compiler dependency, host runner or execution permission. The product records host-Python parse, execution and input/output checks for generated source as `NOT_RUN`; development QC is separate. Full generated-code validation, name/type analysis and general code quality remain open.

## Bounded Python source reading and native evaluation

`code_capability.rs` ports the inherited reader/evaluator/checker as a separate, explicitly bounded subset. The normal input machine seals `code-read:`, `code-evaluate:` or `code-verify:` documents. Core validates the complete one-function source, reads selected AST structures and UTF-8 spans, and—when requested—evaluates the admitted syntax in a native Rust interpreter. Verification evaluates only supplied finite cases. Results remain report artifacts with source/argument/case digests, diagnostics, step counts, observed branches and typed expected/result comparison; they travel through the existing compute/content/render/history path.

The admitted subset supports scalar/list/dictionary values, selected expressions and statements, and fixed builtins. It does not expose Python, OS execution, a compiler, subprocesses, attribute access or external effects. Source/request/value/AST sizes, integer bits, case count, evaluator steps and request deadline are bounded; unsupported syntax stops explicitly. The evaluator does not currently poll an in-progress cancellation request. Eleven authored typed-result/failure comparisons against the frozen interpreter and eleven AST count/depth/structure/span comparisons against CPython 3.11 are recorded in [the B07 bounded-code audit](../audit/b07-bounded-code-capability-route-validation.json). This evidence is finite: complete Python compatibility, static name/type analysis, unseen code quality and full B07 acceptance remain unverified.

## Strict numeric canonicalization before JSON projection

`serde-value` exposes the typed serialization tree before canonical JSON encoding. The domain adapter rejects binary floating-point values, including finite floats, NaN and infinities, instead of letting JSON conversion silently round or collapse them to null. Exact rational/decimal content uses explicit strings; integer record counters retain their declared integer types. Sorted JSON is one versioned wire projection, not an authority or factual-truth proof.

A later [native Linux/Node-WASI vector comparison](../audit/target-conformance.json) observed matching canonical Unicode/exact-string records, digests and lifecycle predicates, with an independent Python hash check. This narrow vector does not establish full Core/storage/effect or independently implemented-backend equivalence and does not establish physical Windows/8GB behavior.

## Bounded meaning comparison instead of inferred equivalence

The Japanese A/B comparison path emits only explicitly recognized features: negation and scope, quantifier bounds, modality, conditional direction, participant roles, voice, time/aspect, attribution, causality, and selected numeric/deadline units. It retains both source statements, names the detected difference, lists shared extracted roles where available, and states that unrecognized material was not checked. If it finds no comparable change, it suspends instead of declaring equivalence. The markers provide a useful inspectable slice of semantic comparison, not a general Japanese parser or an entailment proof.

An open-vocabulary neural model, dictionary-backed parser, or formal grammar is a possible alternative only if it preserves uncertainty, role/scope, source spans, bounded execution, and the same normal-route contracts. This alpha does not compare those alternatives or claim full meaning-transform coverage from marker recognition alone.

## Inspected character-ngram family instead of an assumed universal model

The predecessor model and calculation routes were inspected before selecting the Rust model family. The current `SequenceModel` carries character vocabulary/counts/context, non-neural parameter transformation, exact conditional distribution, sequence scoring and deterministic constrained decoding. Core supplies authorized content units; linguistic scores cannot authorize a proposition or create another final judge.

When Core supplies exactly one complete output surface, the model verifies its token budget and lossless byte projection without multiplying a sequence probability that cannot change the choice. `ModelEmission` records the singleton decoder version and omits `sequence_probability`; multi-candidate ranking still records the exact score. The 8192-bit probability bound remains unchanged for actual ranking. This avoids stopping a valid structured report after its artifact was computed solely because the single candidate's unused exact score grew past that bound. The bounded proof-backed `AskWhy` route now supplies exactly two Core-authored equivalent surfaces that preserve the same proof and disclaimer units; the existing model ranks them and the selected transition reaches the normal rendered response. This demonstrates a finite model effect without extending the model to unrestricted text generation.

A sparse context trie, beam decoder, grammar model or another non-neural architecture is a candidate alternative. The six public model components do not logically imply any one of them. Retaining an inspected ngram family is a compatibility-oriented implementation choice, not a completed comparison against all alternatives. R2-17 and A01–A03 still require the same unseen meaning, quality, learning and resource obligations. The alpha's constrained output construction does not establish general natural-language generation, multilingual fidelity or open-domain answer quality. No external neural response is substituted for native Core results.

## SQLite reference adapter and immutable blobs instead of an ad hoc state log

The store uses SQLite with verified foreign keys, WAL, full synchronization, bounded lock waiting and explicit immediate transactions. Case revisions, input identity, action phases and event references have checked relationships. Content-addressed immutable blobs are written and flushed before their logical references commit. A pre-transaction published orphan is different from a committed revision pointing to a missing blob.

A single custom append-only journal could reduce dependency count but would require independently implementing crash-tail validation, locking, revision CAS, authenticated joins, index recovery and migration semantics. Another database or blob store is valid only if it satisfies the same abstract contracts. Observing a previously attempted exact local file can reconcile the original pending goal; after cancellation the separate effect-ledger observation path cannot restart or commit that cancelled goal. SQLite is selected as an inspectable local reference adapter, not the engine's definition. A database transaction does not atomically deliver a separate file or external message.

Filesystem and power-loss guarantees depend on the actual host/VFS. Directory synchronization and immutable publication must succeed or produce typed failures/unknowns. Full Windows/macOS/other-target durability, interruption matrices and resource measurements remain open gates. No SQLite choice alone supplies encryption or protection against a host principal that can directly read the state directory.

## Native TLS and inherited proxy policy instead of bypasses

`reqwest` uses its blocking client with `native-tls`, preserved inherited proxy settings and ordinary certificate validation. This matches the cloud environment's supplied trust chain and keeps destination policy at its intended boundary. URL grants, HTTPS:443, redirects, bounded bodies, MIME/charset checks and private-address guards remain application-level checks. Source bodies remain evidence data.

A custom socket/HTTP/TLS implementation would require a substantially larger audit surface. A TLS backend with its own trust store could be viable only after explicit CA/proxy conformance; disabling certificate verification is not an alternative. The local loopback HTTP frontend uses Rust standard-library TCP, bounded parsing and a configured token; it is not used to bypass outbound policy or claim deployed HTTPS security.

## FFI in dependencies and the Rust-source boundary

All first-party Rust crates forbid `unsafe` source. This does **not** mean the full dependency graph is pure Rust or free of FFI. `rusqlite`'s bundled SQLite feature compiles SQLite C through its transitive bindings; native TLS uses the host TLS implementation and associated bindings. Their source, versions, licenses and native toolchain requirements belong in the dependency inventory.

Bundled SQLite favors a reproducible SQLite source version over whichever system library happens to be installed; using a system SQLite would reduce compiled bundled code but change provenance/version/feature assumptions. A pure-Rust SQL/storage alternative would need the same relational, crash, migration and resource tests before replacement. Transitive native dependencies are isolated behind typed storage/TLS adapters; they are not permission to introduce undocumented first-party `unsafe`, native calls or target-dependent semantics. Whole-graph supply-chain and platform acceptance remain distinct from first-party compiler lint success.

## Narrow grammar with truthful stops instead of invented understanding

The input machine seals explicit, source-preserving intents for the currently implemented public grammar. Supported mathematical/relation/source tasks use real algorithms and actual data. An unsupported trailing constraint, quoted instruction, language structure, format or provider produces an unresolved intent or typed failure rather than discarding part of the request.

This is a current implementation limitation, not an approved replacement for the required general-language system. General Q&A, writing/code/research quality and all source-discovered capabilities stay in the [full obligations](../audit/implementation-obligations.md). Expanding the grammar must preserve original role, scope, polarity, conditions, permissions and measurable results; adding keyword-specific answers is not a valid substitute.

## Explicit-source text composition instead of content invention

The current B08 slice accepts a strict JSON composition request through the ordinary input/Core path. The caller supplies all material text, byte ranges, block roles, order, companion links, required flags and maximum character count. The compositor adds only fixed layout prefixes and separators and records each output segment against its material or unit directive. Required and condition/caveat units are retained, and the artifact reports omitted optional units.

This follows the inspected legacy contract for composing explicit source slices and keeps a complete source map. It does not discover content, assess the requested purpose, write or rewrite prose, select facts, prove factual truth or meaning equivalence, or measure style and quality. That bounded route is one B08 building block. A separate extractive sentence-ranking operation emits visibly unverified summary candidates with exact source offsets; it does not establish semantic coverage or close the twelve-task writing, editing, rewriting and summary requirement. No fixed task prompt or diagnostic answer is embedded in either route.

## Core-authored relation profile instead of unconstrained generation

The ordinary Japanese/English profile request accepts one explicit subject and requires saved facts. Core builds a finite inventory from that actor's current supported relation proofs, then writes each relation with its guarantee, scope and exact record/dependency IDs. Direct premises and rule-derived facts keep different labels. Conflicting supports are retained side by side. If no supported relation exists, or the finite action/evidence budget is insufficient, Core suspends with a typed reason. The result remains `HYPOTHESIS` because this route does not verify outside-world truth or whether the memory contains every relevant fact.

The output surfaces are Core-authored; the native `SequenceModel` chooses only between two transition phrases around the same claim, provenance and disclosure units. Recovery recomputes the inventory and requires the stored units, dependencies and candidate set to match before confirming a pending local file effect. This creates a useful source-grounded profile on one bounded route without treating text fluency as factual authority. It does not write from open-domain knowledge, assess purpose/style, or close the twelve-task B08 population. The fresh-process observation is in [the known-relation profile route record](../audit/bb-content-known-relation-profile-v69-route-validation.json).

## Extractive sentence candidates with source offsets

The inspected legacy `extractive-要約-v2` ranks complete input sentences by token frequency, a first-sentence weight and a long-sentence penalty, then returns selected sentences in source order. The Rust route keeps this bounded extractive family but preserves exact sentence bytes and source ranges, records selected/omitted indices and score fractions, and exposes the exact source JSON string token. A R2-derived optional character budget accepts only complete sentences, records those excluded by length and continues to lower-ranked sentences that fit; if none fit it suspends without truncation. The budget applies to copied sentence characters, not the fixed disclosure label or layout markers and separators. The V3 artifact records an explicit `bullets` or `paragraph` layout (`bullets` by default). V4 adds zero-based source sentence indices that the caller requires the result to keep; required sentences are reserved before ranking fills remaining slots, while final display remains in source order. Out-of-range indices or required sentences that exceed the sentence/character limits suspend without an artifact. These explicit controls preserve caller-selected source content but do not identify its semantic importance, verify a natural-language content constraint or establish summary coverage. Each copied sentence retains exact source and output byte spans. Core labels the result `HYPOTHESIS` and displays that coverage of purpose, meaning, conditions and negation has not been checked. This is candidate generation; it cannot claim the requested semantic summary is complete or suitable.

## Artifact-based text import and protected editing

`text_editing.rs` accepts explicit original text and protected ranges, or an actual composition/import/editing artifact selected by the caller. Core supplies an actor/case-scoped artifact reader. The editor checks each artifact digest and regenerates the entire canonical record from its source and ancestry before using its text. Replay is bounded by 16 editing revisions and eight million aggregate artifact bytes. This retains existing composition artifacts without changing their serialized schema.

Edits specify exact original byte ranges, expected old text, replacement text and reasons. Every change is checked against one original coordinate space before the batch is applied. Protected quotes, conditions and explicit locks reject changes; insertions at their boundaries update locations. New text points to the current replacement request, while unchanged text points to its actual parent artifact. The editor polls the request deadline; in-progress cancellation polling remains open. The Core adopts the text, records actual consumed artifact hashes and checks normal rendering and any requested local file receipt. This is explicit editing with provenance; correction discovery, semantic equivalence and general writing quality remain open B08 obligations.

The unique-literal location route uses the same bounded replay and actor/case-scoped reader. The caller supplies a nonempty exact search string and replacement; the route accepts only one match, checking overlapping occurrences too. It rejects protected ranges and returns a source-linked proposal with the actual parent artifact digest, byte range and JSON source token spans. It does not change the document. The proposed request can then be submitted to the existing atomic editor, which rechecks its base digest, exact original range, protection and limits. This preserves the inspected `編集箇所を特定` boundary without inventing correction discovery. Missing/repeated terms and natural-language editing intent remain outside this operation.

## Exact-URI source version selection instead of naive aggregation

The same-case source-question consumer groups fetched bodies by their exact recorded `final_uri` and uses the uniquely latest `observed_at_unix_ms` body/parser identity for lexical candidate extraction. A newer observation with different bytes supersedes that URI's older body for the current answer; the older packet references and hashes remain in the source-version artifact and result dependency graph. Repeated observations of the same body/parser identity remain linked as one active source version, not as additional independent sources. Different content/parser identities tied at the latest observed time suspend rather than selecting by packet order. A result that mixes `LIVE` and `FIXTURE` bodies also suspends.

Exact URI equality is a conservative identity boundary, not a claim that two different URLs are independent publishers or that identical content proves agreement. The bounded Japanese-substring/English-token matcher still returns extractive `HYPOTHESIS` candidates; this choice does not establish semantic relevance, source independence, contradiction analysis or factual truth. Existing V1 source-question artifacts remain replayable during local-file recovery; new artifacts use a separate V2 operation identifier.

## Effects and frontend authority

The local file writer receives a persisted authorized `ATTEMPTED` record binding exact target/bytes/action identity. It reports actual observations. Core alone validates content/render/write outcomes and changes the goal state. Existing different files are not overwritten; uncertain physical outcomes remain unknown rather than generating a fresh action identity.

An atomic external transaction or a general exactly-once claim is not inferred from local SQLite or stable hashes. Remote delivery needs a provider-specific reconciliation/idempotency contract. CLI actor configuration is trusted host input; HTTP binds request identity to a configured authenticated local actor and caps grants/budgets. A public multi-user service requires its own deployment and access-control design and tests.
